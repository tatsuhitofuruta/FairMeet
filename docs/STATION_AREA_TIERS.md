# 駅の栄え度tier表

## 目的

移動時間だけでは候補駅が同程度に並ぶ場合に、集合後の店探しや待ち合わせのしやすさを軽く反映する。

このtierは駅周辺の雰囲気を断定するものではない。MVPでは手動管理の補助データとして扱い、終電判定、営業時間判定、店舗検索、Google Maps API連携は実装範囲に含めない。

## 主指標

主指標は人口ではなく、国土数値情報の「駅別乗降客数データ」とする。

人口は「住んでいる人の多さ」に寄りやすく、集合駅としての店探しや待ち合わせのしやすさを直接表しにくい。駅別乗降客数は「その駅に人が集まる量」を表しやすいため、栄え度tierの初期生成に向いている。

将来の生成フローでは、駅別乗降客数を駅名、都道府県、緯度経度で `station_database` の駅に突合し、最終的には station code keyed の `STATION_AREA_TIERS_BY_CODE` に落とし込む。

補助指標は次の扱いにする。

- 駅周辺の商業・飲食POI数: 店探しのしやすさに近いが、Google Maps API連携は別issueで扱う
- 昼間人口・メッシュ人口: 繁華街性の補助には使えるが、住宅地を過大評価しやすいため主指標にはしない
- 手動補正: 乗降客数だけでは拾いにくい繁華街性、駅直結商業、近接駅エリアを補う

## キー

`station_database` の station code をキーにする。駅名は同名駅や表記揺れがあるため、tier表の主キーにはしない。

実装では `src/lib/stationAreaTiers.ts` の `STATION_AREA_TIERS_BY_CODE` を更新する。

```ts
{
  1130205: {
    tier: 4,
    reason: '渋谷駅周辺の代表的繁華街・飲食集積',
    updatedAt: '2026-06-11',
  },
}
```

## tier定義

| tier | 表示 | 判断基準 |
|------|------|----------|
| 0 | 未設定 | 手動tier表に未登録。スコア補正には使わない |
| 1 | 生活圏 | 日常利用の飲食店や店舗はあるが、広域の待ち合わせ候補としては控えめ |
| 2 | 地域拠点 | 複数路線または駅前商業があり、近隣からの集合には使いやすい |
| 3 | 広域拠点 | 商業・飲食・乗換利便性が高く、広域の集合候補になりやすい |
| 4 | 主要繁華街 | 大規模ターミナルまたは代表的な繁華街で、店探しと待ち合わせの選択肢が厚い |

## 手動判定の基準

手動で更新するときは、乗降客数ベースの初期tierに対する補正として扱う。少なくとも次のうち複数を満たすかを確認する。

- 複数路線の乗換駅、または広域移動の結節点である
- 駅直結または駅前に大型商業施設、商店街、飲食街がある
- 待ち合わせや飲食店探しの目的地として一般的に使われる
- 同じエリア内で別駅が近接している場合は、駅名ではなく station code ごとに登録する

主観を抑えるため、`reason` には「好き」「便利そう」ではなく、商業集積、飲食集積、複数路線、広域ターミナル性などの観察可能な理由を書く。

## スコアリング反映

tierは直接加点・減点しない。既存の公平性スコアを主判定にしたまま、スコア差が3分以内の近い候補群だけで高tierを先に並べる。

このため、移動時間として明確に不利な駅が、繁華街という理由だけで上位に割り込むことはない。3分という閾値は `STATION_AREA_TIER_SCORE_WINDOW_MINUTES` で管理する。

## UI表示

手動tierが登録されている候補駅だけ、結果カードに `栄え度 {tier}` を表示する。未登録駅は表示しない。

## 今後の接点

外部指標を使う場合でも、生成結果はこの station code keyed の表に落とし込む。Google Maps API、店舗件数、営業時間、終電判定は別issueで扱い、この表では参照先の追加や生成手順のメモに留める。

乗降客数からの自動生成を追加するときは、次の順で進める。

1. 国土数値情報の駅別乗降客数を取得する
2. 駅名、都道府県、緯度経度で `station_database` の駅に突合する
3. 乗降客数の分位点で tier 1〜4 の初期値を作る
4. 主要繁華街や近接駅エリアだけを手動補正として差分管理する

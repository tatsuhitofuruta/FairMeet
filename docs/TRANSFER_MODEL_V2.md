# v2 乗換モデル検討メモ

Issue: [#4 v2: 実際の乗換を考慮した経路評価を検討する](https://github.com/tatsuhitofuruta/FairMeet/issues/4)

## 結論

v2 の最小方針は、現行の静的ホスティングとブラウザ内完結を維持しながら、所要時間とは別に「乗換負担」を推定する静的補正を追加することとする。

Google Maps Platform Routes API などの外部経路 API は、実際の乗換待ち、徒歩、発着時刻、乗換回数を得られる可能性がある一方で、API キー、課金、利用規約、キャッシュ制約、リクエスト数の爆発を持ち込む。そのため v2 の本線にはしない。外部 API は、少数の代表ケースを検証するための任意の調査手段に留める。

## 現行モデルが考慮していること

現行実装は `station_database` から静的な鉄道グラフを作り、Dijkstra で最短の概算時間を求める。

| 要素 | 現行の扱い | 実装箇所 |
|------|------------|----------|
| 同一路線の乗車 | 路線詳細の隣接駅をスポーク間エッジとして接続し、直線距離、迂回係数、表定速度、停車ロスから所要時間を推定する | `scripts/build-graph.mjs` |
| 同一駅内の乗換 | 駅ハブと `(駅, 路線)` スポークを 2.5 分で接続する。別路線へ移るとスポーク -> ハブ -> スポークで合計 5 分が加算される | `scripts/build-graph.mjs` |
| 初乗り・降車の待ち/改札相当 | 出発駅ハブから路線スポークへ 2.5 分、到着路線スポークから候補駅ハブへ 2.5 分が加算される。ただし同一駅が候補の場合は 0 分になる | `scripts/build-graph.mjs`, `src/lib/dijkstra.ts` |
| 近接する別駅の徒歩連絡 | 駅ハブ間に `3 + 15 × 距離km` 分の徒歩連絡エッジを張る。距離 0.8km 以下、または同一 `original_name` かつ 1.2km 以下を対象とする | `scripts/build-graph.mjs` |
| 相対的な公平性 | 各メンバーの最短概算時間から、最大時間、平均時間、格差を使って候補駅を順位付けする | `src/lib/scoring.ts` |

## 現行モデルが考慮していないこと

| 要素 | 現行の限界 | v2 での扱い |
|------|------------|-------------|
| 実際のホーム移動 | 駅ごと、路線ペアごと、改札内外ごとの移動時間差を持たない。東京・新宿などの大駅も地方の小駅も同じ 5 分として扱う | 主要駅だけ静的な駅別補正を持つ。路線ペア別補正はデータが確保できるまで見送る |
| 乗換待ち | 運行間隔、曜日、時刻、方向を持たないため、待ち時間を評価できない | 路線別の平均ヘッドウェイを持てる場合だけ追加する。終電判定は別 issue とする |
| 直通運転 | 路線名が変わる境界で実際には列車に乗ったままでも、別路線スポークへ移るため乗換ペナルティが発生しうる | 直通ペアを静的データで持ち、指定ペアだけ乗換負担を軽くする案を検討する |
| 乗換回数 | 時間に含まれるだけで、候補表示やスコア上の別指標になっていない | 最短路探索で二次指標として数える、またはエッジ種別から概算回数を返す |
| 列車種別 | 各停・快速・特急・新幹線の停車駅パターン、待避、追加料金を持たない | v2 では扱わない。新幹線だけ現行の速度モデルを維持する |
| 時刻依存 | 朝夜の混雑、終電、運休、遅延を持たない | v2 では扱わない。終電判定とリアルタイム性は別 issue とする |
| 実徒歩経路 | 近接駅徒歩は直線距離ベースであり、地下通路、横断可否、出入口差を持たない | v2 では静的な近接駅補正リストがあれば上書き可能にする |

## 外部 API 案

候補としては Google Maps Platform Routes API の Transit routing がある。公式ドキュメント上、公共交通のルートは電車・地下鉄・バスなどを扱い、駅間徒歩、到着/出発時刻、停留所、路線詳細、運賃などのフィールドを取得できる。また、少ない徒歩や少ない乗換を優先する設定も用意されている。

ただし、FairMeet のユースケースでは全候補駅に対して「人数 × 候補駅」の経路評価が必要になる。Google Routes API には行列計算もあるが、公式ドキュメントでは Compute Route Matrix が origin×destination の要素数で課金され、`TRANSIT` の最大要素数は 100 とされている。9,000 駅級の全探索とは相性が悪い。さらに Routes API は利用に API キーまたは OAuth トークンと課金設定が必要であり、Google Maps Platform のサービス規約では Routes API 由来の緯度経度キャッシュが 30 日に制限される。

外部 API を採用する場合の位置づけは次の通り。

| 観点 | 評価 |
|------|------|
| 精度 | 実際の乗換待ち、発着時刻、徒歩、乗換回数を反映しやすい |
| コスト | API キー、課金、クォータ管理が必要になる |
| 静的ホスティング | フロントエンドだけに API キーを置くと制御が難しい。サーバまたはプロキシが必要になる |
| キャッシュ | API レスポンス由来の永続的な静的グラフ化は利用規約上の確認が必要になる |
| 検索規模 | 全駅候補の評価ではリクエスト数が大きすぎる。上位候補の再ランキング用途なら現実的 |
| v2 方針 | 本線にはしない。代表ケースの妥当性確認、または将来のサーバ版での上位候補再ランキングに限定する |

## 静的データ補正案

v2 の本線は、現行の `graph.json` を拡張して、時間と別に乗換負担を扱う静的補正とする。

### 案 A: エッジ種別を持つ graph v2

`edges` に種別を追加するか、別配列でエッジ種別を持つ。

```jsonc
{
  "version": 2,
  "edges": [[0, 9372, 25, "hub"], [9372, 9373, 12, "ride"]]
}
```

この案では、Dijkstra の距離計算は既存の重みを維持しつつ、確定経路から「駅内乗換」「徒歩連絡」「乗車区間数」を集計できる。欠点は、現在の Dijkstra は距離配列だけを返しており経路復元をしていないため、前駆ノードまたは二次指標を持つ実装変更が必要になること。

### 案 B: 乗換負担を重みに混ぜる

ハブエッジや徒歩連絡エッジの重みを調整し、乗換が多い経路を自然に下げる。

この案は実装が小さいが、時間と負担の意味が混ざり、候補表示で「なぜこの駅が下がったか」を説明しづらい。公平性の比較も実分数ではなくなるため、v2 の本線にはしない。

### 案 C: 主要駅・近接駅だけ補正テーブルを持つ

手作業または公開可能な静的データから、主要駅の構内移動補正、近接駅の徒歩補正、直通ペアを持つ。

```jsonc
{
  "stationTransferPenalty": {
    "1130101": 8
  },
  "walkingOverride": {
    "1130208:2800218": 9
  },
  "throughServicePairs": [
    ["東京メトロ副都心線", "東急東横線"]
  ]
}
```

この案は精度の伸び幅が限定されるが、静的ホスティング、説明可能性、データサイズの面で現行方針と相性が良い。v2 の最小実装では、まずこの補正テーブルを空でも読める構造にし、主要駅だけ段階的に増やす。

## スコアリング方針

v2 では、表示上の所要時間は引き続き分単位の概算時間として扱う。その上で、乗換負担を二次指標としてスコアに入れる。

推奨式:

```ts
effectiveScore = timeScore + transferBurdenWeight * meanTransferBurden
```

`transferBurden` は次の要素を足した概算値とする。

| 要素 | 初期値 |
|------|--------|
| 駅内乗換 1 回 | 1.0 |
| 徒歩連絡 1 回 | 1.5 |
| 主要駅の追加構内負担 | 0.0 から開始し、補正テーブルがある駅だけ加算 |
| 直通運転の境界 | 0.0 または軽減値 |

スコアに入れる強さは小さく始める。たとえば `transferBurdenWeight = 2` 分相当なら、平均で乗換 1 回多い候補は 2 分だけ不利になる。時間の公平性を主目的にしたまま、「同じくらいの時間なら乗換が少ない駅」を上げる調整になる。

## v2 の最小成果物

v2 で実装する最小範囲は次の通り。

1. `graph.version = 2` でエッジ種別を保持できるようにする。
2. 既存の時間最短 Dijkstra は維持し、結果表示の分数を変えない。
3. 経路復元または二次指標により、候補ごとの平均乗換負担を算出する。
4. スコアは時間を主、乗換負担を副として扱う。
5. 静的補正テーブルは空データから開始し、主要駅・近接駅・直通ペアを後から追加できる形にする。

v2 で扱わない範囲は次の通り。

- 終電判定
- リアルタイム運行情報
- Google Maps API などの本番利用
- 駅の栄え度 tier
- 列車種別別の停車駅モデル
- 運賃、特急料金、予約要否

## 実装メモ

- 現在の `GraphData.version` は `1` 固定なので、後方互換を考えるなら `GraphDataV1 | GraphDataV2` の union にする。
- `buildAdjacencyList` は現在、エッジ種別を捨てる。v2 では `AdjacentEdge` に `type` を持たせるか、Dijkstra 用の軽量 adjacency と経路説明用 metadata を分ける。
- 乗換負担を正確に出すには、距離だけでなく前駆ノードが必要になる。全候補の経路復元が重い場合は、Dijkstra の状態に「同距離なら負担が少ない経路を優先する」二次指標を持たせる。
- v1 の `graph.json` を読める期間を残し、`version` で分岐する。既存の `public/data/graph.json` がない環境でも unit test が動く状態は維持する。
- 外部 API の結果を静的データへ取り込む場合は、データのライセンス、キャッシュ期間、派生データ扱いを確認するまで実装しない。

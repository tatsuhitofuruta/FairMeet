# FairMeet 要件定義書

## 1. 目的

複数人で集まるとき、全員の最寄駅を入力するだけで「誰か一人だけが極端に遠い」という不公平を避けた集合駅を提案するWebアプリを提供する。

利用シーン: 飲み会・勉強会・打ち合わせの場所決め。幹事がメンバーの最寄駅を聞いて入力し、候補駅を見ながら店を探す。

## 2. スコープ

### 対象
- 日本国内の鉄道駅（JR・私鉄・地下鉄・新幹線。廃駅は除く）
- 2〜10人の最寄駅入力
- 鉄道移動のみを考慮した所要時間の概算

### 対象外（明示的にやらないこと）
- 時刻表・運行ダイヤに基づくリアルタイム経路検索を、候補順位付けの主ロジックには使わない
- バス・徒歩・飛行機・フェリーでの移動
- 運賃計算
- 店舗・スポット検索
- ユーザー登録・履歴保存などのサーバサイド機能

### 将来スコープ（v2候補）
- 終電判定: 解散予定日時を入力し、候補駅から各メンバーの最寄駅へ終電で帰れるかを評価する
- 実際の乗換評価: ホーム移動、乗換待ち、直通運転、乗換回数など、現行の固定ペナルティでは表しきれない負担を評価する
- Google Maps API連携: アプリ内の店舗検索、徒歩移動、地図表示が必要になった場合に扱う。料金・利用規約・キャッシュ制約は公式情報で要確認
- 駅の栄え度tier: 駅ごとに集合場所としての使いやすさを表すtierを持たせ、移動時間だけでは選びにくい候補を補正する

## 3. 機能要件

| ID | 要件 |
|----|------|
| F-1 | 最寄駅を2〜10人分入力できる。入力欄の追加・削除ができる |
| F-2 | 駅名はオートコンプリートで入力する。漢字・ひらがな（読み）の前方一致で候補を出し、同名駅は都道府県で区別できる |
| F-3 | 同じ駅を複数人が入力してもよい |
| F-4 | 全駅を候補として、各メンバーの出発駅からの推定所要時間を計算し、公平性スコアで順位付けした上位5駅を提示する |
| F-5 | 探索モードを3つから選べる: 公平重視（最大所要時間を最小化）/ バランス / 合計重視（全員の合計時間を最小化）。既定は公平重視 |
| F-6 | 各候補駅について、駅名・都道府県・乗り入れ路線・メンバーごとの所要時間・最大/平均所要時間を表示する。所要時間の差が一目で分かる棒グラフ表現を含む |
| F-7 | 鉄道網がつながっていない駅の組み合わせ（例: 沖縄のゆいレールと本州の駅）は、到達不能である旨を明示する |
| F-8 | 候補駅から地図アプリ（Googleマップ）へのリンクを提供する。APIキー不要のMaps URLで、地図・飲食店・カフェ・居酒屋検索を開ける |
| F-9 | 所要時間が概算（実ダイヤ非考慮）であることを画面上に明示する |
| F-10 | データ出典（station_database, CC BY-SA 4.0）のクレジットを表示する |
| F-11 | スコアが近い候補では、station code keyed の駅栄え度tierを補助的な並び替えに使える |
| F-12 | 候補駅ごとに、Transit APIを使って各メンバーの最寄駅から候補駅までの実ルートを手動で確認できる |

## 4. 非機能要件

| ID | 要件 |
|----|------|
| N-1 | 候補算出はフロントエンドのみで完結する（静的ホスティング可能）。実ルート確認は任意操作として外部APIを呼び出す |
| N-2 | 駅データ・路線グラフはビルド時に前処理し、静的ファイルとして同梱する |
| N-3 | グラフデータの転送量は gzip 後 2MB 以下を目標とする |
| N-4 | 10人入力時でも候補算出は1秒以内に完了する |
| N-5 | スマートフォンでも操作できるレスポンシブUI |
| N-6 | UI言語は日本語 |

## 5. 所要時間モデルの前提

時刻表を使わないため、所要時間は以下の近似モデルで推定する（詳細は設計書）:

- 乗車時間 = 駅間直線距離 ÷ 表定速度 + 停車ロス
- 乗換 = 固定ペナルティ（同一駅内）+ 徒歩時間（近接別駅間）
- 待ち時間・運行本数は考慮しない

この近似により実際の所要時間と±20〜30%程度の誤差が生じうる。アプリは「最速経路の案内」ではなく「相対比較による公平な集合駅の提案」を目的とするため、全員に同じモデルを適用する限り順位付けの妥当性は保たれる、という立場を取る。

## 6. データソース

- [Seo-4d696b75/station_database](https://github.com/Seo-4d696b75/station_database)（CC BY-SA 4.0）
  - 駅: 9,372件（名称・かな・緯度経度・都道府県・乗入路線・廃駅フラグ）
  - 路線: 636件（駅の並び順 = 隣接関係を含む）
- ライセンス義務: 出典表示、改変データ（graph.json）の同一ライセンス継承
- 駅栄え度tier: station code をキーにした補助データ。主指標は国土数値情報の駅別乗降客数とし、手動補正を許容する。Google Maps API、店舗検索、終電判定は対象外
- [Transit API](https://api.transit.ls8h.com/): 候補カードでの実ルート確認に使う。認証不要・読み取り専用・CORS開放のAPIとして扱い、候補順位付けの自動計算には使わない

### 将来追加する可能性があるデータ

| データ | 用途 | 備考 |
|--------|------|------|
| 終電データ | 候補駅から各メンバーが帰宅できるかを判定する | GTFS / GTFS-JP などの時刻表データの入手元・更新頻度・ライセンスが要確認 |
| 乗換補正データ | 主要駅の構内移動、近接駅の徒歩、直通運転などを補正する | 現行の静的グラフと両立する範囲から始める |
| Google Maps API | 店舗・スポット検索、徒歩時間、地図表示 | APIキー管理が必要になるため、静的サイトだけで完結する現行方針とは分けて設計する |
| 駅の栄え度tier生成元 | 候補駅の実用性スコアを補正する | 初期版は手動管理のtier表から始め、将来は乗降客数や店舗数などの指標で更新できるようにする |

## 7. 受け入れ基準

1. `npm run build:data` で graph.json が生成される（ネットワークからソースデータ取得）
2. `npm run test` が全件パスする
3. `npm run build` が警告なく完了する
4. ブラウザで「渋谷・大宮・横浜」を入力すると、3人の所要時間バランスが取れた現実的な候補（例: 都心部のターミナル駅）が上位に出る
5. 「那覇空港・東京」のような到達不能ペアで適切な警告が出る
